# Codex 工作流规范

## 开始任务

1. 读取 `AGENTS.md`、`docs/README.md`、`codex-rules/global-AGENTS.md` 和本次任务相关规则。
2. 检查相关设计文档和 `docs/architecture/open-decisions.md`。
3. 区分用户已经明确的要求、能从仓库或工具查证的事实，以及仍需用户决定的事项。
4. 明确任务是否触及定位、信息架构、内容模型、路由、SEO、部署、用户数据、评论、订阅或产品服务。
5. 若触及上述范围，先更新 `docs/` 中的设计与待决策问题，再写代码。

## 用户意图与不确定性

- 禁止臆测用户的想法。不得根据模糊措辞、过往习惯、行业惯例或 Codex 自身偏好，擅自补全用户未明确表达的意图、偏好、优先级、验收标准、业务事实或授权范围。
- 能通过仓库文件、已有设计文档、工具输出或权威资料确认的客观事实，应先查证并引用依据，不能把未经查证的猜测当成事实。
- 查证后仍不确定，或事项涉及用户偏好、需求取舍、范围变化、公开表达、交互行为、架构选择、数据与隐私、成本、外部副作用、不可逆操作或验收结果时，必须明确写出：已知事实、不确定项、可选方案及各自影响，并请用户作出决定。
- 用户明确决定前，不得实施依赖该决定的部分；不得用“合理假设”“默认方案”“更保守方案”“先替用户决定”或“可否决的判断”代替确认。可以继续不受待决策事项影响、且能够独立验证的工作。
- 用户的决定应写入对应设计文档、契约或任务记录；仍未决定的事项应标为“待确认”，不得写成已确定事实，也不得提前落入代码或公开文案。

## 执行原则

- 小步推进，优先完成最小可验证闭环。
- 只依据用户明确要求和已查证事实执行，不自行补全需求。
- 不引入复杂基础设施，除非当前阶段设计文档已说明必要性。
- 不用营销文案掩盖未实现能力。
- 不为了交付速度加入多余兜底来掩盖问题；应暴露真实失败原因，定位并解决根因。

## 文档先行

以下变化必须先改设计文档：

- 新增或变更公开页面结构、导航、路由、内容栏目或 SEO 策略。
- 新增或变更产品服务、收费、订阅、评论、讨论或反馈入口。
- 新增用户数据收集、访问分析、第三方脚本或表单提交。
- 新增部署方式、构建框架、CMS、后端服务或数据库。

## 验证与汇报

完成任务后汇报：

- 修改了哪些文件。
- 做了哪些验证。
- 哪些问题仍待确认。
- 是否引入用户数据采集或第三方服务；默认应为未引入。

代码改动后按项目现状运行相关检查，例如：

- 当前基础门禁：`npm run quality`。
- 后续已配置时运行格式化、lint、typecheck 和测试。
- 前端 UI 改动必须启动页面并做实际渲染或截图验证。

若无法运行检查，需要说明原因。
