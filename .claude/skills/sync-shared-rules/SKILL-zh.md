# 并行仓库规则同步

[English](SKILL.md) | 中文

## 触发场景

- 用户明确要求把 project-scaffold（或当前仓库）里的某条规则同步到其他并行仓库。
- 用户修改了 `.claude/rules/*.md` 或 `codex-rules/rules/*.md` 里的通用规则后，问"要不要/怎么同步到其他项目"。
- 用户提到台账里列出的任一仓库需要跟进最新规则。

## 前提

先读 [`docs/architecture/sibling-repo-sync-zh.md`](../../../docs/architecture/sibling-repo-sync-zh.md) 台账：仓库清单（路径、规则文件位置、commit 校验机制、CI）+ 同步记录。这是免去每次重新探查全部仓库的关键，但**台账可能滞后于仓库实际状态**（仓库所有者可能手动改过），只能当起点，不能盲信。

## 黄金工作流（绝不跳过，跳步就是制造新漂移）

1. **读台账**：确认这次要同步的规则是什么、目标仓库有哪些、每个仓库的规则文件位置和 commit 校验机制。
2. **逐仓库探查现状**：对每个目标仓库实际 Read 相关文件（`CLAUDE.md` / `AGENTS.md` / `codex-rules/rules/*.md` / commit 校验脚本或配置），不要假设台账仍然准确；顺带跑 `git status --short` 确认没有未提交的其它工作会被误动、记录当前分支。
3. **按各自机制适配，不整段照抄**：同一条规则在不同仓库的落地方式不同——有的靠 shell 正则 hook，有的靠 Python 脚本，有的靠 commitlint 配置，有的没有机器强制、只是文档约定；有的有 CI 有的没有。文案和（如涉及）校验逻辑都要按目标仓库现状改写，而不是复制 project-scaffold 的原文。
4. **实测再落地**：
   - 改了 commit 格式相关的正则/脚本/commitlint 配置，必须现场构造"应通过"和"应拒绝"各一条示例跑一遍（`python3 -c`、直接调用 hook 脚本、或 `pnpm exec commitlint`），确认行为符合预期再写回文件。
   - 不要凭"看起来对"就交付。
5. **写回并本地提交，不自动 push**：每个仓库改完用该仓库自己的提交格式提交一次（正好触发该仓库自己的 commit-msg hook，是最后一道实测）；是否 push、是否开 PR，问用户再定，不要自作主张推远程。
6. **更新台账**：把这次同步的规则、涉及仓库、日期、任何顺带修的细节，追加进台账的"同步记录"表格。

## 常见坑点

- **“正则很宽松所以不用改代码”是陷阱**：宽松正则（如 `.+` 放行任何内容）意味着规则只是摆设、不会真的拦截不合规提交。为了让文档和门禁一致，应按目标仓库真实的 Conventional Commit 结构收紧，并用真实示例验证通过/拒绝两种情况。
- **commitlint/husky 仓库的 `header-max-length`**（常见 100 字符）仍要求主题简洁；必要时先用 `pnpm exec commitlint` 实测示例。
- **没有 CI 的仓库不要编造 CI 条款硬凑一致**：写清楚"待接入 CI 后生效"，用该仓库现有的等效本地检查命令做临时收尾要求，而不是假装它有 CI。
- **`.githooks` / `core.hooksPath` 类仓库**：如果本地从没执行过启用命令，新加的 hook 文件不会生效。发现这种情况可以直接执行启用命令（通常是仓库文档里写明的标准一次性步骤，非破坏性操作），或明确告诉用户还差这一步。
