# PlantUML in Markdown

English | [Chinese](SKILL-zh.md)

Use PlantUML for compact technical diagrams whose editable source belongs directly in Markdown. Use the project `archify` Skill instead when the result needs a polished standalone viewer, rich interaction, guided exploration, theme switching, or canonical high-resolution bitmap export.

Never maintain equivalent PlantUML and Archify sources for the same illustration. One document may use both for different views.

## Required workflow

Every new or changed PlantUML block must complete this loop:

1. Choose the diagram type that matches the information.
2. Extract every Markdown PlantUML block to a separate `.puml` file.
3. Compile each file with the configured local JAR and inspect all failures.
4. Repair only the diagnosed source, then compile it again.
5. Write the verified sources back to Markdown.
6. Re-extract and compile the complete document.
7. Run `npm run gen:plantuml`, inspect the rendered SVG, and run `npm run check:plantuml`.

Use the bundled helpers:

```bash
export PUML_JAR=/absolute/path/to/plantuml.jar
bash .claude/skills/plantuml-in-markdown/scripts/extract_and_compile.sh path/to/doc.md
python3 .claude/skills/plantuml-in-markdown/scripts/write_back.py path/to/doc.md <reported-output-dir>
```

Success requires exit code 0 and a non-empty rendered image. A plausible-looking source is not evidence of successful compilation.

## Type selection

| Information to express | Preferred PlantUML type |
| --- | --- |
| Static structure, layers, component dependencies | Component diagram |
| Request/response or messages across participants | Sequence diagram |
| One-way processing or data transformation | Activity diagram with `partition` |
| Algorithms with loops and conditional branches | Activity diagram |
| Entities, relationships, or class structure | ERD/class diagram |
| Status transitions and request lifecycles | State diagram |
| Multiple actors with several internal steps each | Swimlane activity diagram |

Do not default to swimlanes. They are appropriate only when multiple actors each own meaningful internal steps. A relay such as A → B → C usually needs an activity diagram; a call that waits for a return usually needs a sequence diagram.

## Repository contract

- Use exactly `plantuml` for the Markdown fence language.
- Each block must contain `@startuml` and `@enduml`.
- Each block must be followed, with at most one blank line, by a non-empty local `.svg` image reference for GitHub rendering.
- The Markdown block is the only editable source. The SVG is generated by `npm run gen:plantuml`.
- Do not use `!include`, `!includeurl`, `!import`, or related directives. Diagrams must be self-contained and compile under PlantUML's `SECURE` profile.
- Keep authored text in the document's primary language. Preserve exact identifiers, protocols, commands, and product names.
- Do not hand-edit generated SVG or compare its bytes across machines; PlantUML layout depends on the JAR, JVM, Graphviz, and installed fonts.

## Common syntax failures

- Keep a swimlane name on one source line; use the literal `\n` for a visual line break.
- Do not switch swimlanes inside `if`, `else`, or `while` blocks.
- Place `note right ... end note` after a concrete action.
- Prefer `repeat while (condition?) is (yes) not (no)` for explicit loop exits.
- Avoid empty `else` branches.
- Do not mix activity, class, state, and sequence syntax in one diagram.
- In sequence diagrams, activate and deactivate the callee; explicitly activating the initiator often produces duplicate activation errors.

## Delivery checklist

- The selected diagram type matches the information.
- Every extracted source compiles with exit code 0.
- The write-back step is complete and the whole document compiles again.
- `npm run gen:plantuml` produces a non-empty SVG for every block.
- The SVG has been visually inspected for readable labels, correct direction, and complete content.
- `npm run check:plantuml` passes.
