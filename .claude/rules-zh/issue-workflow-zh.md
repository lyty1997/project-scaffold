# Issue 编写与拆解规范

[English](../rules/issue-workflow.md) | 中文

约束 issue（Linear / 任务）的编写方式与拆解策略：管"动手之前 issue 怎么写、怎么拆"。
适用于新增 / 修改模块、跨多步骤或一次写不完的复杂任务；纯文档、单文件小修复可豁免（但涉及跨模块契约仍适用）。

## 一、新模块开发 issue —— 描述里必须写成操作步骤

不允许只写"实现 XX 模块"就开工。issue 描述里必须把下面两组步骤写进验收清单：

### 1. 先对齐 API，再动手对接联调
- 写出本模块对外接口签名：函数名 / 路由 path+method / 事件名
- 逐字段标注参数与返回值：字段名、类型、可选/必选、枚举取值范围、错误形态（错误码+结构）
- 标注跨层契约字段：谁带 tenant_id / revision / 关联 ID，在哪一层注入
- 与上下游 issue 互相引用，确认双方对同一份签名达成一致
- 理由：签名/字段名/类型/枚举/错误形态四项不匹配会在联调时炸；动手前花十分钟对齐，等价于先定好 `.h` 头文件再各自写 `.c`

### 2. 上下游没就绪 → 用模拟数据自测，拿到证据才验收
- 用 mock / stub / fixture 构造上游输入，覆盖正常路径 + 至少一条异常/边界路径
- 对下游用 stub 接住输出，或断言输出结构符合已对齐的契约
- 跑出并留存"输入 → 输出"证据（测试输出 / 日志 / 截图），贴进 issue
- **验收门槛：没有输入输出证据的模块一律视为未完成，不得勾 Done**
- 理由：不允许用"等下游就绪再说"代替自测；每个模块联调前要能独立证明契约成立，否则 bug 层层叠加无法定位

## 二、复杂任务 —— 先拆解，分派子 issue 逐个分步解决

遇到复杂问题 / 复杂编码（跨多模块、跨多状态、一次写不完、或实现路径不明确）时：
1. **先拆解，不直接开工**：拆成边界清晰、可独立验收的子任务
2. **每个子任务建 sub-issue**：挂父 issue 下，父 issue 只做汇总与里程碑
3. **标注子 issue 依赖顺序**（blocks / blocked-by），避免乱序开工
4. 每个子 issue 若是新模块仍遵守"第一节"
5. **逐个分步闭环**：一次只推一个子 issue 到"有证据的 Done"再开下一个，禁止多个半成品并行堆积

拆解粒度：单子 issue 半天到两天可闭环、能独立出证据为"刚刚好"；多到管理成本超实现成本→合并；仍跨 3+ 模块、写不完→继续拆。
